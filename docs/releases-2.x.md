# Выпуск NexSSH 2.x (Slint)

Разработка идёт в `codex/2.0.0-slint`. Версия приложения задаётся в
`native/Cargo.toml`; версия 1.x в корневом `Cargo.toml` остаётся отдельной.
Сейчас локально разрабатывается `2.0.0-alpha.2`; её публикация пока не выполняется.

## Патчноут 2.0.0-alpha.2

- **Один экземпляр приложения:** повторный запуск показывает открытое окно и восстанавливает его из трея или свёрнутого состояния.
- **Настройки клавиатуры:** исправлено наложение поясняющего текста на соседние строки.
- **Статистика терминала как в 1.x:** адрес сервера, uptime, CPU, RAM, диск, графики и подсказки. Опрос приостанавливается при сворачивании и скрытии панели.
- **Файловый менеджер:** перенесено оформление 1.x — компактная шапка, путь, колонки имени/размера/даты, строки, иконки, прокрутка, контекстные меню и нижние панели.
- **Файловые операции:** создание файлов и папок, переименование, удаление с подтверждением, права доступа, копирование пути, переход в терминале и стартовая папка сервера. Создание файла не перезаписывает существующий.
- **Панель файлов:** ширина 300–640 px, сброс до 380 px двойным щелчком; на узкой панели скрывается дата. Исправлен двойной щелчок по папкам.
- **Отрисовка терминала:** устранено смещение обычного, жирного и цветного текста относительно сетки, включая дробный масштаб Windows.
- **Выбор шрифта:** список установленных моноширинных шрифтов и встроенный JetBrains Mono. Выбор применяется сразу и сохраняется после перезапуска; недоступные шрифты получают встроенную замену.
- **Оптимизация обновлений терминала:** неизменившиеся элементы текста сохраняются, обновляются только отличающиеся; временные буферы подсветки используются повторно. В локальных нагрузочных замерах снизились затраты CPU и немного уменьшилось потребление памяти при включённом GPU.
- **Информация об ОЗУ при GPU-отрисовке:** рядом с переключателем добавлен значок ⓘ. При наведении появляется пояснение о возможном росте потребления оперативной памяти, при уходе мыши оно исчезает. При включении GPU выводится уведомление с напоминанием о перезапуске. Добавлены русский и английский тексты.

## Как устроены обновления

| Установленная версия | Откуда получает обновления |
| --- | --- |
| 1.x | Только стабильный `latest.json`, как раньше |
| 2.0.0-alpha/beta/rc | Новые предварительные сборки 2.0.0 через `preview.json`; стабильная 2.0.0 имеет приоритет |
| Стабильная 2.x | Только стабильный `latest.json` |

Предварительные релизы публикуются с `prerelease=true` и `latest=false`.
В них **нет `latest.json`**, поэтому 1.x их не предложит. Тестовый клиент
находит `preview.json` среди assets версионных GitHub Releases; отдельного
подвижного тега `preview` не требуется. Учитываются до 100 последних релизов.

Когда будет готова финальная версия, нужно собрать **новую версию `2.0.0`**
и выпустить тег `v2.0.0`. Простого снятия галочки prerelease с alpha-релиза
недостаточно: канал определяется версией внутри приложения. Стабильная сборка
получает `latest.json` и становится Latest. Тогда её увидят и 1.x, и тестовая
2.0; после установки обе будут получать стабильные обновления.

До финального выпуска можно продолжать публиковать стабильные 1.x отдельным
workflow `Release 1.x`. После выхода стабильной 2.x выпуск 1.x не переключает
Latest обратно на 1.x.

## Локальная сборка без публикации

Нужны Windows x64, Rust stable с поддержкой Rust 1.95+, Node.js 22, Python 3.11+
и Windows SDK (MSVC, MakeAppx, SignTool).

```powershell
npm ci
cargo test --locked -p nexssh-slint
python -m unittest discover -s scripts -p test_native_release.py
./scripts/native-release.ps1
```

Результат: `target/native-dist/NexSSH_2.0.0-alpha.2_x64-setup.exe` и
`SHA256SUMS.txt`. Выходная папка должна быть пустой: для следующей проверки
можно передать `-Out target/native-dist-next`.

Скрипт собирает настоящий Slint exe, добавляет иконку и сведения о версии,
встраивает пакет меню Проводника и использует NSIS-упаковщик Tauri CLI.
WebView2 и Tauri runtime в приложение не включаются. Установщик совместим
с идентификатором и каталогом прежнего NexSSH. Для обновления с 1.x сохранены
оба ключа платформы: `windows-x86_64` и `windows-x86_64-nsis`.

Нужная приложению `vcruntime140.dll` берётся из x64 Redistributable установленного
Visual Studio и размещается рядом с exe. Отдельная установка Visual C++ Runtime
для этого не требуется; используется стандартное
[локальное развёртывание Microsoft](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method?view=msvc-170).

Предварительный установщик заменяет установленную 1.x. Данные остаются в
`%APPDATA%\NexSSH`, пароли — в системном хранилище; настройки Slint сохраняются
в `native-settings.json`, исходный `settings.json` сохраняется. Это одна линия
установки с выбором канала, а не два независимо установленных приложения.

Без ключей локальная сборка не получает подпись автообновления; пакет
Проводника подписывается временным сертификатом. Такой установщик предназначен
для локальной проверки. Для публикации используется `-RequireSignature`,
который требует существующие ключи, свежую сборку и запрещает подмену public key.

## GitHub Actions

`Release Slint 2.x` запускается:

- при push тега `v2.*.*` — собирает, проверяет и публикует;
- вручную, `dry_run=true` по умолчанию — только собирает артефакты;
- при изменениях самого процесса выпуска в ветке — только проверяет сборку.

Для workflow_dispatch новый workflow должен сначала быть доступен в основной
ветке GitHub. Ветка с изменениями процесса выпуска также запускает dry run
при первом push; выпуск по тегу использует workflow из помеченного коммита.

Уже используемые секреты репозитория:

- `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`;
- `EXPLORER_SIGNING_CERT`, `EXPLORER_SIGNING_PASSWORD`.

Ключ обновлений должен совпадать с public key из `desktop/tauri.conf.json`.
Native build берёт его оттуда же. Менять ключ при переходе 1.x → 2.x нельзя:
установленная 1.x должна проверить подпись новой сборки.

Перед публикацией pipeline запускает unit tests, clippy, полную проверку
установки/обновления/удаления меню Проводника, а затем установку поверх
последней стабильной 1.x с проверкой сохранности файлов данных. Эти установочные
тесты изменяют приложение и сертификаты на одноразовом runner; их не следует
запускать на рабочем ПК. `native-upgrade-test.ps1` явно запрещает такой запуск.

Установщик подписывается с привязкой к версии (`signer sign --app-version`).
Собранный клиент повторно проверяет подпись и подписанную версию через
`--verify-update <manifest.json> <installer.exe>` перед публикацией. Сначала
создаётся draft со всеми assets, затем он публикуется целиком. Повторный
запуск не перезаписывает уже существующий релиз.

После проверки изменений выпуск первой alpha выполняется так:

```powershell
git push origin codex/2.0.0-slint
# Дождаться успешного dry run и CI, проверить артефакт установщика.
git tag v2.0.0-alpha.1
git push origin v2.0.0-alpha.1
```

Следующий выпуск: изменить версию в `native/Cargo.toml`, выполнить `cargo check`
для обновления `Cargo.lock`, сохранить изменения и создать соответствующий тег.

## Проверка загрузки в интерфейсе

Для текущих сборок есть UI-тест с подписанной фикстурой `9999.0.0`.
Высокая тестовая версия позволяет проверять обновление после смены номера alpha;
эта фикстура не публикуется и подписана отдельным тестовым ключом:

```powershell
$env:NEXSSH_UPDATER_PUBLIC_KEY = (Get-Content native/tests/fixtures/updater/test.key.pub -Raw).Trim()
cargo build -p nexssh-slint --features slint/mcp
Remove-Item Env:NEXSSH_UPDATER_PUBLIC_KEY
python native/tests/updater_ui.py target/debug/nexssh-slint.exe
```

Это отдельная тестовая сборка с тестовым public key; её не следует распространять.
Тест загружает фикстуру, проверяет отказ от установки и отклонение подмены файла
и версии. Сам установщик он не запускает.

`NEXSSH_UPDATE_URL` позволяет подать тестовый manifest с localhost. HTTP разрешён
только для loopback, остальные URL и перенаправления требуют HTTPS. Этот параметр
не отключает проверку подписи. `NEXSSH_UPDATER_PUBLIC_KEY` — только параметр
компиляции для тестовых сборок, runtime заменить public key не может.

Клиент ограничивает размеры ответов, проверяет подпись и подписанную версию
перед показом «Установить», затем повторно перед запуском NSIS. Установка требует
подтверждения закрытия сеансов. Установщик ждёт завершения процесса приложения,
чтобы дать ему сохранить настройки и закрыть подключения, затем перезапускает
обновлённый клиент. Подпись обновлений не является Windows Authenticode-подписью
exe; этот процесс использует существующий механизм доверия NexSSH 1.x.
